Test Validation Fix (Commit: 2ef971e)

Fixed date/timestamp validators to handle YAML datetime objects:

  • YAML parser converts ISO 8601 timestamps to datetime.datetime objects

Fix:

  • is_valid_date(): Accept both str (YYYY-MM-DD) and datetime.date objects
  • is_valid_iso_timestamp(): Accept both str (ISO 8601) and datetime.datetime objects with timezone
  • If YAML successfully parsed it into a datetime object, consider it valid

Key Decisions

Priority notation choice:

  • Selected p0/p1/p2/p3 over other formats (critical/high/medium/low, 1-4, etc.)
  • Rationale: Concise, sortable, industry-standard in engineering teams
  • Lexicographic sorting works correctly (p0 < p1 < p2 < p3)

tmp/ directory approach:

  • Chose soft delete (mv to tmp/) over immediate deletion (rm)
  • Rationale: Recovery window, audit capability, less destructive
  • Weekly manual cleanup instead of automatic deletion
  • User maintains control over when cleanup happens

APPS.md relocation:

  • Moved from root to standards/apps.md
  • Rationale: App registry is framework documentation, belongs with standards
  • Better organization, reduces root directory clutter
  • Removed from naming exceptions (now follows kebab-case in standards/)

Testing framework:

  • Selected Python + pytest over bash scripts or other frameworks
  • Rationale: Readable tests, native YAML support, great error messages
  • Focus on deterministic validation logic (not AI parsing)
  • Start minimal (Phase 1), iterate to comprehensive coverage
  • Validators accept both string and datetime objects (YAML flexibility)

Testing Framework Insights

YAML parsing behavior:

  • YAML automatically converts date strings to datetime.date objects
  • YAML automatically converts ISO 8601 timestamps to datetime.datetime objects
  • Validators must handle both string format (for manual validation) and datetime objects (from YAML parsing)
  • This is actually a feature, not a bug - if YAML can parse it, it’s valid

Test design philosophy:

  • Test what can go wrong, not what’s guaranteed to work
  • Focus on boundary conditions and edge cases
  • Use fixtures for both valid and invalid examples
  • Parameterized tests enable testing all vault files efficiently

Future phases:

  • Phase 2: ULID uniqueness tests, comprehensive naming convention tests
