our plan is solid, and (crucially) it matches a pattern that already exists in the wild: “Markdown as source of truth, generated SQLite index for fast query + validation + AI tooling.” You do not need to start from scratch.

High-level evaluation of your plan

What you’re proposing (as an architecture)

  • Source of truth: Markdown + YAML frontmatter (local-first, human-readable, Git-friendly)

  • Derived store: SQLite index (queryable, fast, can support FTS)

  • Index pipeline: parse → validate → emit DB → flag/fix issues

  • UI: Obsidian (editor, backlinks, graph, plugins)

  • AI integration: use the SQLite index + file paths as retrieval layer; optionally expose as MCP / local service

  • Versioning: Git

This is a very sane architecture. It scales better than “Obsidian-only metadata querying” because SQLite gives you:

  • stable queries

  • performance on large vaults

  • a clean interface for AI tools (RAG, semantic search, metadata filters)

  • deterministic validation/fixes

Key risk to manage

Don’t let SQLite become a competing source of truth. It must remain:

  • derived

  • rebuildable

  • throwaway

  • schema-controlled

If you keep that invariant, you get the best of both worlds.

Existing models you can reuse (so you don’t reinvent the wheel)

1) MarkdownDB (direct hit for “Markdown → SQLite index”)

MarkdownDB is essentially your “sqlite index generated from markdown” requirement, already packaged. It indexes markdown files (including frontmatter/tags) into SQLite. (GitHub)

How it helps you:

  • jump-start the index layer quickly

  • gives you a known DB schema pattern (files table + join tables like tags)

  • lets you focus your effort on validation + fixers + AI integration rather than basic indexing

Where you’ll likely extend it:

  • custom frontmatter schema enforcement

  • error reporting + auto-fix pipeline

  • Obsidian-specific concepts (wikilinks, vault-relative paths, attachments)

2) “Obsidian Index Service” pattern (watch vault → SQLite)

There’s an open-source pattern that does exactly what you described: monitor an Obsidian vault directory and index Markdown files—metadata and full content—into SQLite. (GitHub)

How it helps you:

  • shows a practical architecture for “continuous indexing”

  • good starting point if you want a daemon/service instead of a CLI rebuild

3) Dendron’s “indexing + schema-ish metadata” approach (conceptual model)

Dendron is markdown + frontmatter and has a strong “indexing server” concept in its ecosystem. It’s VS Code–based rather than Obsidian-based, but the architecture is relevant: local-first notes, generated indexes, and conventions/templates. (Dendron)

How it helps you:

  • conventions for required frontmatter

  • systematic “note type” approaches

  • operational patterns for large vaults

4) Obsidian plugin ecosystem (UI-side helpers)

Obsidian itself has a very active plugin ecosystem. You can reuse:

  • indexing helpers (even if not SQLite)

  • metadata maintenance patterns

  • AI plugins for in-editor workflows (Obsidian)

This won’t replace SQLite indexing, but it can reduce how much custom UI you build.

The “best reuse path” (what I’d recommend)

If your goal is a general-purpose, consistent base (framework, not content), the best path is:

Reuse for indexing, build for correctness + AI

  • Use MarkdownDB (or similar) for the base SQLite index (GitHub)

  • Add your framework layers:

    1. Schema validation for frontmatter (JSON Schema or equivalent)

    2. Error reporting (machine-readable report + human-friendly summary)

    3. Optional auto-fix with “safe fixers” (timezone normalization, ULID format fix, missing defaults, etc.)

    4. AI integration that reads from SQLite (filters + FTS + embeddings table if you want it)

This gets you to a working, maintainable system with minimal reinvention.

A concrete “framework target” (what “done” looks like)

Repo structure (suggested)

  • _vault/ (your Obsidian vault content — unchanged)

  • _framework/

    • schemas/ (frontmatter schemas by type)

    • indexer/ (parse → validate → sqlite)

    • fixers/ (optional auto-fixes)

    • reports/ (latest validation run results)

    • ai/ (RAG layer; MCP server optional)

    • cli/ (commands: index, validate, fix, report)

  • markdown.db (generated; in .gitignore)

CLI contracts

  • lexi index → rebuild sqlite

  • lexi validate → report errors, no modifications

  • lexi fix → apply safe fixes + produce a diff report

  • lexi doctor → “vault health” summary (counts, missing fields, broken links, etc.)

That’s the general-purpose base you can reuse forever.

Do you need Logseq DB mode or “database-first” tools?

Probably not. Logseq’s DB/SQLite mode trends toward a single database file as primary storage, which fights your requirement of Git-first markdown source-of-truth. Even Logseq community guidance often points to sticking with Markdown mode if you want Git/SyncThing workflows. (Logseq)

So: keep your plan. Don’t flip the storage model.

Bottom line

  • Your plan is strong.

  • You can reuse MarkdownDB as the indexing substrate (big acceleration). (GitHub)

  • You can reuse the “watch + index to sqlite” service pattern if you want continuous updates. (GitHub)

  • Your unique value is the validation + fixer pipeline + AI layer tuned for Obsidian + Git.

If you want, I’ll propose two concrete implementation tracks (simple CLI rebuild vs continuous daemon) and a minimal schema set that makes the framework general-purpose without being overdesigned.

This is a foundational decision, so I’ll be opinionated and explicit. The goal is: boring, predictable, refactor-safe, AI-friendly, Obsidian-friendly, Git-friendly.

1. File naming pattern

Recommendation: ULID-only filenames (with optional human alias in frontmatter)

Yes — use ULID as the filename.
Do not encode meaning in filenames.

Canonical filename

01JGFNLP8Z2XK4H7MZ9VYQ8C4A.md

Why this is the right choice

  • Rename-proof: titles, semantics, hierarchy can change freely

  • Stable identifiers across refactors, moves, and merges

  • Git-friendly: diffs remain clean; moves don’t break links

  • AI-friendly: ULID is a perfect primary key

  • Obsidian-safe: works fine with wikilinks

How humans navigate instead

  • title frontmatter (primary)

  • aliases frontmatter

  • folder structure (high-level grouping only)

  • Obsidian search, backlinks, Bases, SQLite queries

Filenames are for machines. Titles are for humans.

What not to do

Avoid:

  • 2026-01-15-my-thoughts.md

  • task-fix-schema.md

  • note-xyz.md

  • mixed patterns (doc-024.md, task-127.md, etc.)

Those create long-term entropy.

One exception (optional)

You may allow:

01JGFNLP8Z2XK4H7MZ9VYQ8C4A--schema-design.md

…but only if:

  • ULID is first

  • everything after -- is non-canonical and disposable

  • your tooling ignores suffixes completely

If you don’t need this, skip it.

2. Linking rule (critical)

Always link by filename ULID, never by title:

Your indexer can optionally support title-based backlinks for convenience, but ULID must be the ground truth.

3. Standard core frontmatter (minimal, universal)

This is the non-negotiable core. Every file has these.

Field-by-field rationale

uid

  • Must match filename ULID exactly

  • Enforced by validator

  • Never changes

type

Controls schema, views, behavior.

Examples:

note | doc | task | project | person | asset | session | backlog

Use a small, closed set. New types require a schema file.

title

  • Human-readable

  • Can change freely

  • Used in Obsidian UI, Bases, AI summaries

status

Lifecycle state (normalized per type but same field everywhere):

draft | active | on-hold | completed | deprecated | archived

Avoid ad-hoc statuses.

created-at

  • ISO 8601

  • Timezone required

  • Immutable once set (except fixer repair)

4. Strongly recommended (but optional) core fields

These are extremely high-value and worth standardizing early.

aliases

  • Enables human-friendly wikilinks

  • Preserves continuity across renames

  • Your indexer can auto-backfill aliases when titles change

tags

  • Flat, lowercase

  • Avoid hierarchical tags (a/b/c)

  • Use links for structure, tags for facets

source

Useful for AI + provenance:

  • manual

  • imported

  • ai-generated

  • transcript

  • web

5. Fields that should never be in the core

Keep these out of the universal base:

  • business-specific fields (estimate, amount, priority)

  • ownership (assignee)

  • scheduling (due-at)

  • relationships (parent, depends-on)

These belong in type-specific schemas, not the core.

6. Type-specific frontmatter (pattern)

Each type extends the core schema.

Example: task

Your validator should:

  • enforce allowed fields per type

  • flag unknown fields

  • allow shared optional fields via $ref

7. Folder structure guidance (lightweight)

Folders are organizational hints, not identity.

Example:

_database/
  notes/
  tasks/
  docs/
  projects/

Rules:

  • Files may move freely between folders

  • Folder ≠ type (type lives in frontmatter)

  • Indexer must not infer meaning from path alone

8. Fixers you should ship on day one (naming + core FM)

  • Filename ↔ uid mismatch fixer

  • Missing uid → generate ULID + rename file

  • Missing created-at → fill from git or filesystem

  • Title missing → derive from first heading or filename

All with --dry-run first.

9. Summary (architectural stance)

Yes: ULID-only filenames.
Yes: small, universal frontmatter core.
Yes: type-specific schemas layered on top.
No: semantic filenames.
No: folder-as-meaning.

This gives you:

  • long-term stability

  • easy refactors

  • clean SQLite indexing

  • predictable AI retrieval

  • Obsidian ergonomics without lock-in

If you want, next we can:

  • lock down the status model per type

  • define the minimal global schema file

  • or design the ULID generation + rename strategy so adoption is painless.
