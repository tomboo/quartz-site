Framework v2: Multi-Vault Platform Architecture

Status: Planning Created: 2025-12-26 Last Updated: 2025-12-26

Executive Summary

Redesign the Personal Operating System framework as a portable, scalable platform that can be deployed to multiple project vaults with different requirements, supporting both technical power users and non-technical end users at scale.

Context

The Lexi Ecosystem (3-tier)

lexi-depot (stable backend - Firebase/Firestore)
  ↓ provides data storage
lexi-vault (CLI orchestration - rapid iteration)
  ↓ manages vaults
Project Vaults (Obsidian vaults - where framework lives)
  - vault-personal-tom (Tom's personal OS)
  - lexi-you-da-hoe (Lexi's writing vault)
  - Future: additional project vaults

Framework v2 is vault-internal infrastructure that provides database-like structure, schema validation, and component patterns within Obsidian project vaults.

Scale Requirements

Current (vault-personal-tom):

  • 220 files across 8 backend tables
  • Single user (Tom - technical)
  • Active development/iteration

Near-term (migration targets):

  • Notion migration: Thousands of pages with integrations and automation
  • Lexi’s writing vault: ~8,000 scenes written over 20-30 years
  • Multiple novels and projects
  • Non-technical user (Lexi)

Total scale: 10,000+ items across multiple vaults

Problem Statement

Current v1 Limitations

  1. Not designed for multi-vault deployment - Tightly coupled to single vault
  2. No formal schema system - Ad-hoc Python validation, prone to drift
  3. No clear separation - Apps mix UI and data concerns
  4. Not scalable - 8,000 files will strain current structure
  5. Not portable - Can’t easily share framework between vaults
  6. No release model - Can’t have stable (Lexi) + dev (Tom) versions

Design Review Findings

Initial critique (assuming 220 files, single user):

  • Over-engineered
  • ULIDs overkill
  • Too much validation
  • Fighting Obsidian’s simplicity

Revised assessment (with 10K+ files, two vaults, release model):

  • ✅ ULIDs justified (bulk imports, cross-vault uniqueness)
  • ✅ Schema validation essential (can’t manually review 8K files)
  • ✅ Multiple databases necessary (different vault types)
  • ✅ Database-like approach appropriate at this scale
  • ✅ Python tooling needed for bulk operations

Framework v2 Architecture

Core Concepts

1. Components (renamed from “apps”)

  • UI/presentation layer
  • Declare database/table dependencies in manifest
  • Can use one or more databases
  • Future: Python automation scripts

2. Databases (semantic names)

  • Self-contained with schema.json
  • Multiple databases per vault (e.g., core, docs, writing)
  • Each database has multiple tables
  • Portable across vaults

3. JSON Schema

  • Machine-readable schema per database
  • Defines all tables in that database
  • Validates frontmatter properties
  • Enables template generation
  • Self-contained for portability

4. Shared Framework

  • Base property templates (uid, created-at, timestamps)
  • Validation tooling (Python libs)
  • NLP parser, template engine
  • Slash commands
  • Health checks

Key Design Decisions

Schema Inheritance & Portability

  • Each database schema is self-contained (no external references)
  • Template schema exists as source of truth for base properties
  • New databases are generated from template (gets base properties)
  • Portability: Copy database folder = copy everything it needs

Release Model

  • Tom’s vault = development environment
  • Periodic stable releases exported to Lexi’s vault
  • Version pinning - Lexi’s vault declares framework version
  • Migration scripts provided with releases
  • Changelog documents breaking changes

Implementation Approach

Phase 1: Proof of Concept

  • Create database-docs/ with schema.json
  • Test on real data (copy existing items for validation)
  • Create components/docs/ with manifest
  • Validate pattern works before full migration

Phase 2: Migration Strategy

  • database-core/ = existing _database/database-core/ tables + schema
  • Update existing components to use manifests
  • Gradual migration, maintain compatibility

Phase 3: Lexi Vault

  • Design database-writing/ schema for scenes/characters/novels
  • Test with subset of 8,000 scenes
  • Stable release process

Open Questions

  1. Database naming: Semantic (core, docs, writing) or numbered (database-001)?

    • Decision: Semantic names for clarity

  2. Schema granularity: One schema per database, or per table?

    • Decision: One per database using type property to differentiate tables

  3. Template sharing: How are base properties shared across databases?

    • Decision: Template schema + generation, self-contained result

  4. First test case: New database or migrate existing?

    • Decision: Test on copy of real data to validate upward compatibility

  5. Framework distribution: Git submodule, copy/sync, monorepo, or package?

    • Decision: Copy with version pinning (Tom iterates, Lexi gets releases)
